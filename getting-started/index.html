Getting started

Requirements¶

  • Julia 1.11 or later. AirLang’s Project.toml uses the [sources] local path entries that Julia 1.11 introduced.

  • Air.jl 0.3 and AirDB.jl 0.1, checked out beside this repository. AirLang depends on both as local path packages.

  • PostgreSQL only if you want database-backed persistence. The default in-memory database needs no server.

Installation¶

Clone the three repositories as siblings. AirLang’s Project.toml resolves ../Air.jl and ../AirDB.jl, so the directory names matter:

mkdir -p ~/Code && cd ~/Code
git clone https://github.com/noahbenson/Air.jl
git clone https://github.com/noahbenson/AirDB.jl
git clone https://github.com/noahbenson/AirLang.jl
cd AirLang.jl
julia --project=. -e 'using Pkg; Pkg.instantiate()'

Pkg.instantiate() resolves the path dependencies and downloads the registered ones (Air uses DataStructures; AirDB uses LibPQ). Precompiling happens on first use:

julia --project=. -e 'using AirLang'

Running air¶

bin/air is the command line. With no arguments it starts a read-eval-print loop; -e evaluates one chunk of code; any other argument is a file to load:

./bin/air                              # the REPL
./bin/air -e '(+ 1 2)'                 # => 3
./bin/air -e 'using AirLang; (println "hi")'
./bin/air program.air                  # load a file
./bin/air --serve program.air          # load, then stay up (ssh-server, …)

--serve keeps the process alive after the files and -e chunks are evaluated, so an ssh-server (or another process resource) keeps serving until SIGINT or SIGTERM. This is how the Docker container stays up.

The -e chunks and files in one invocation share an environment, so definitions made by an earlier -e are visible to a later one. The REPL reads a form across lines while the reader reports an unterminated form, string, or block comment (with a ...> continuation prompt) and sets AIR_HISTORY to a file that each complete input is appended to, for use with external line editors such as rlwrap.

From Julia, the same entry points are available as functions:

using AirLang, AirDB

env = Env(db = MemoryDatabase())          # a private in-memory database
air_eval(env, read_air("(+ 1 2)"))        # => 3
air_string(air_eval(env, read_air("(let (x=2) (* x 3))")))   # => "6"

air_eval, read_air, air_string, air_pretty_string, air_repl, open_airdb!, and close_airdb! are exported. Env carries the process database; see Databases.

At the REPL, (help) prints an introduction to the language, (doc NAME) documents any builtin or definition, and (doc .air) lists every name the language ships with. See Documentation and the builtin catalogue.

Libraries¶

lib/ in this repository is the first entry of AIR_LIBPATH, the :-separated (Windows: ;) list of directories air searches when a library is first needed; the default is <repo>/lib followed by ~/.air/lib. A library is a directory holding an init.air:

lib/
  math/
    init.air
(using math (twice 4))       # loads lib/math/init.air if needed
(.lib.math.twice 4)          # the loaded namespace is reachable too

lib/README.md describes the layout; Loading files and libraries covers the loader in detail.

The Docker image¶

The repository ships a Dockerfile and a docker-compose.yml. The image is a slim Julia runtime with AirLang and its dependencies precompiled; it contains no build toolchain, and the host’s ./lib is mounted at /air/lib and used as the library path.

The sibling checkouts are passed as named build contexts (BuildKit, the default in current Docker):

docker build -t airlang \
    --build-context air=../Air.jl \
    --build-context airdb=../AirDB.jl .

Or use the compose file, which names the same contexts, starts a PostgreSQL sidecar, and brings up air as an SSH server:

docker compose up -d --build         # air (SSH on :2222) plus PostgreSQL
docker compose up -d --wait          # ...and block until air is listening
docker compose logs -f air           # follow the air log
docker compose down                  # stop both; the database volume survives

docker compose up -d publishes port 2222 at once but air takes a few seconds to load the interpreter and evaluate startup.air before it listens. A connection in that window is accepted by Docker’s proxy and reset during key exchange, so ssh reports an immediate close; --wait blocks on the compose healthcheck until the port answers, and ssh -v shows the same window as kex_exchange_identification: read: Connection reset by peer.

docker compose up -d runs air --serve startup.air in the container; add --build on the first run and after changing the image’s source. The repository’s startup.air opens the PostgreSQL sidecar as the namespace .db, creates an example user with a placeholder SSH key, and starts (ssh-server :sshd port=2222 bind="::"); compose publishes port 2222 and mounts ./lib at /air/lib, the first AIR_LIBPATH entry. Edit startup.air to set your own user name and public key (replace the base64 blob with the contents of ~/.ssh/id_ed25519.pub), then docker compose restart air. Log in with:

ssh -p 2222 <your-user>@localhost

:: is dual-stack: ssh localhost tries ::1 before 127.0.0.1, and a server bound only to 0.0.0.0 (IPv4) leaves Docker’s proxy with nowhere to send the IPv6 attempt, which the client reports as an immediate close during key exchange. Every SSH refusal is silent on the wire by design; to see why one failed, run JULIA_DEBUG=AirLang docker compose up -d and follow docker compose logs -f air.

--serve is the one CLI flag the container needs: it runs the files and -e chunks, then keeps the process alive so its ssh-server (and any other process resource) keeps serving until SIGINT/SIGTERM ends it.

One-off commands use the same image and mounts:

docker compose run --rm air -e '(+ 1 2)'   # => 3

bin/air-docker is a thin wrapper that runs the image with the same command line as bin/air and mounts ./lib; it is the easy way to get an interactive REPL:

./bin/air-docker                     # REPL
./bin/air-docker -e '(+ 1 2)'        # => 3
./bin/air-docker program.air

Inside the container the library path is /air/lib (the mount) and Julia’s depot is /opt/julia.

Running the tests¶

The test suite needs only the default in-memory database; the PostgreSQL tests run when AIRLANG_TEST_PG_URL names a server:

julia --project=. test/runtests.jl

# ... with PostgreSQL:
AIRLANG_TEST_PG_URL="postgresql://air:air@localhost/air" \
    julia --project=. test/runtests.jl

julia --project=. -e 'using Pkg; Pkg.test()' is the same suite under Pkg’s isolation. The docker-compose.yml sidecar provides a PostgreSQL server with user, password, and database air:

docker compose up -d postgres
